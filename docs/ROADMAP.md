# 产品路线图

## 当前：完成商家 Demo 验收

主要功能已经实现。完成标准包括：顾客预约可在商家端查看；商家取消后顾客看到正确状态；关店保留已有预约并阻止新预约；恢复接单按剩余容量重算；权限、幂等、日期范围与并发规则符合设计。

优先完成以上实际流程，再扩大功能范围。安排手机验收，记录设备、账号角色、结果和问题，不能仅凭入口可见认定验收完成。

## 试用与正式运行准备

- 替换示例服务、价格、介绍、联系电话和营业时间。
- 明确服务／营业时间由谁维护，以及如何安全更新已有日程。
- 配置每日补齐预约日程与有界清理任务，验证失败告警。
- 实测平台权限、索引、限流、资源费用告警和备份恢复。
- 准备独立生产环境与生产业务初始化流程；确认适用的平台发布要求。

当前商家页面没有服务编辑、价格修改或周营业时间编辑界面；这些数据通过受控配置与控制台管理。是否增加可视化编辑，应根据店主实际维护频率另行确定。

## 下一阶段：预约信用与防恶意占位

这是设计文档规划的后续需求，目前尚未实现：

| 能力 | 开发前需要明确 |
| --- | --- |
| 到店／爽约记录 | 谁确认、何时可标记、误判如何撤销；时间已过不能自动算完成或爽约 |
| 临近取消 | 距开始多久算临近取消；商家取消是否排除在顾客违规之外 |
| 预约限制 | 统计周期、触发次数、限制时长、恢复方式与历史记录 |
| 身份增强 | 是否需要验证手机号；验证手机号不等同于完整实名核验 |
| 异常行为识别 | 如何识别频繁预约取消、占位与多账号行为，并减少误伤 |
| 顾客信用记录 | 哪些事实可记录、如何展示和纠正，避免直接引入不透明评分 |

建议先实现可纠正的事实记录与人工临时限制，再依据真实使用情况制定自动规则。“几次爽约就拉黑”目前没有已确认的阈值。

## 待产品决定

商家取消、预约提醒是否接入消息通知，仍需确定触发场景、用户授权和失败后的处理方式；当前产品不会自动发送取消通知。

## 当前不做

支付、定金和退款，多商家／多门店，员工与技师排班，多资源预约，以及独立财务、营销、CRM 或分析平台。保持单店、单服务提供者的业务边界。
